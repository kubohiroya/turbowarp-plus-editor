SCRATCH ADDONS · TURBOWARP ADDONS · TURBOWARP-PLUS-EDITOR

Three ways to add features to the editor

Four documents that compare Scratch addons, TurboWarp addons and the sockets of TurboWarp-Plus-Editor, specify how Plus builds in its added features, and explain how to build a new one.

In these documents, an added feature is something Plus builds into the editor itself on top of standard TurboWarp, and an extension is a Scratch or TurboWarp extension that a project loads.

01 · SHORT ARTICLE

Addons reach in from outside; Plus gets called from inside

There are three main ways to add features to a Scratch-family editor. The core difference is which side calls the other: the feature code or the editor.

The official Scratch 3 editor has no mechanism for users to add features. The community browser extension Scratch Addons fills that gap. It injects scripts into scratch.mit.edu pages, then looks for on-screen elements and internal state from the outside and adds features to them.

TurboWarp took the editor-oriented addons from Scratch Addons and bundled them into its own build. The code style and API are nearly the same, but they run as part of the editor instead of as a browser extension.

TurboWarp-Plus-Editor reverses the direction. Its fork of scratch-gui has named sockets that say "use this if something is supplied here", and the build binds Plus's implementation to them. When nothing is supplied, the fork behaves exactly like upstream TurboWarp.

The addon approach doesn't touch the editor itself. In exchange, when the page structure changes, addons silently stop working. The Plus approach leaves call lines in the fork, but its contracts are pinned by types and tests. It can also handle work that must take effect before a project loads, and replace the whole layout.

Plus's main features are the layout, extension review and the save flow. None of them fit the "add from outside" model, so there is little point in Plus aiming for addon compatibility. Small features that can be removed again are written, like addons, so they can be attached later and detached.

The detailed comparison is in 02 Comparison and conclusion, and the list of sockets is in 03 Spec.

02 · COMPARISON AND CONCLUSION

Comparing the three approaches, and why Plus chooses sockets

This compares the mechanism, when each takes effect, how each breaks and how each is toggled. It ends with the advantages of the Plus approach and the reasons for them.

1. Scratch Addons: a browser extension injected into the page

Scratch Addons is a browser extension for Chrome or Firefox. Each addon has its own manifest that declares its name, description, tags, settings, whether it is on by default and which pages it runs on. When you open a matching page, the browser extension injects the addon's userscripts and userstyles into it.

A userscript is an async function that receives ({addon, console, msg}). It waits for elements to appear with addon.tab.waitForElement, obtains the VM and Blockly through traps, and watches Redux state. The official editor has no sockets, so everything has to be found from the outside.

2. TurboWarp addons: bundled, running on the same API

TurboWarp pulls the editor addons of Scratch Addons into its own source with a script called pull.js. It applies TurboWarp's patches to the upstream code (the tw branch of TurboWarp/addons), rewrites it further with regular expressions, and places the result in src/addons/. The current fork contains 81 addons, six of which are TurboWarp's own tw- addons.

At run time, api.js recreates the addon object of Scratch Addons and passes it in. APIs that only exist in a browser extension, such as login information, are absent. In their place there are spots tailored to TurboWarp's screen, such as the shared spaces of appendToSharedSpace (eight of them, including stageHeader, afterGreenFlag, afterStopButton and afterSoundTab). mediarecorder, which adds a "Record" button to the menu bar, also uses this mechanism: it looks for the element next to the File menu and inserts itself there.

3. TurboWarp-Plus-Editor: bound to sockets at build time

Plus does not add a single file to its scratch-gui fork that upstream doesn't have. It puts getHostIntegration() in src/addons/hooks.js, a file upstream also has, and 28 files other than hooks.js ask for values by name, as in getHostIntegration()?.EditorLayout.

In the distributed build, webpack's ProvidePlugin binds __TW_GUI_HOST__ to this repository's site/gui-integration/index.ts. From there it connects to the integration object in site/plus-integration.ts and to the versioned @kubohiroya/turbowarp-* npm packages. When the GUI is built on its own, __TW_GUI_HOST__ doesn't exist, the getter returns null, and the GUI behaves like upstream.

4. When each takes effect

The three approaches differ in when a feature starts working. Addons attach asynchronously after the page or GUI starts running, so they are a poor fit for work that must be in effect before a project loads. Plus can pass such work, like extension review, synchronously through a socket, so it is settled before loading.

5. How each breaks when upstream changes

Addons look for CSS module class names by prefix (scratchClass, [class*='menu-bar_file-group'] and so on). When upstream changes the page structure, the search fails and nothing happens. Plus's sockets are calls written into the fork's source, so a clash with an upstream change stops at the merge conflict, the type check or the integration tests.

8. Conclusion: why the Plus approach is better

For TurboWarp-Plus-Editor to add features to TurboWarp, the current approach of placing named sockets in the fork and binding implementations at build time suits it better than the addon approach. There are six reasons.

  1. It can take effect before the projectExtension review and the list of trusted extensions must be settled before a project loads. Addons attach asynchronously after startup and can't guarantee that order. Sockets are read synchronously at render time.
  2. It can replace whole structuresThe Dockview layout, stage panel, sprite list and save flow are not additions to the existing screen. Doing them as addons would mean hiding upstream's DOM and rebuilding it. A socket can take a React component or a reducer fragment as is.
  3. The contract is visible and testableAddons connect through hashed class names and on-screen text. Plus's sockets have fixed names and arguments, which test/plus-integration.test.ts and test:gui-integration can pin down. When upstream changes, tests stop the change instead of letting it break silently.
  4. The diff from upstream stays smallEvery socket is optional; with nothing passed in, the fork behaves like upstream. Only call lines remain in the fork, and it has zero files that upstream lacks. When upstream updates are merged, conflicts are limited to those call lines.
  5. Implementations are reusable, versioned partsThe implementations live in @kubohiroya/turbowarp-* npm packages, each with its own versions, tests and releases. The same packages work in the single-HTML player that Packager produces. Addons only run inside their editor.
  6. It connects to runtime extensionsSome sockets are exposed to extensions as Scratch.gui.stageControls and Scratch.gui.blockEditors, so extensions such as the camera can register their own controls in the Editor's control bar. The addon API was not designed to be used from extensions.
COSTS WE ACCEPT

There is no screen where users toggle individual features. The fork's call lines must be maintained with every upstream update, and adding a feature requires a rebuild. Third parties cannot add features at run time either. Features that aren't part of the editor itself, however, can be added as runtime extensions through the control bar API.

That said, small features in area A of Fig. 7 are written like addons: "attached later, removed with dispose". That makes them easy to move to the addon form if we ever want users to toggle them. We will not rebuild existing features to be addon-compatible.

03 · SPECIFICATION

How TurboWarp-Plus-Editor builds in added features

This defines how Plus's added features reach the forked scratch-gui, the list of sockets, the rules they follow, startup flags and the API exposed to runtime extensions.

1. Three repositories and the direction of dependency

Plus's added features span three repositories. Dependencies go one way; upstream knows nothing about downstream.

2. Binding at build time

The fork's src/addons/hooks.js, a file upstream also has, contains this getter.

/* global __TW_GUI_HOST__ */
// The distributing build supplies this module; standalone GUI builds have no extra host.
export const getHostIntegration = () =>
    (typeof __TW_GUI_HOST__ === 'undefined' ? null : __TW_GUI_HOST__);

The distribution build's scripts/site/webpack.config.cts uses ProvidePlugin to bind __TW_GUI_HOST__ to site/gui-integration/index.ts. Nothing depends on assigning a global at run time or on startup order. The values the fork reads come in two layers.

4. Socket rules

Every socket follows these rules, and so must any new socket.

  1. Optional. With no value, the fork behaves like upstream TurboWarp. Helpers return an empty default ([], {}, null).
  2. GUI internals arrive as arguments. The host never imports the fork's reducers or UI. The fork passes Modal, the lazily loaded ScratchBlocks, the logger and Redux action creators at call time (for example createCancelSecurityLoad(initialState, defaultProjectId, LoadingState, integration)).
  3. Anything attached can be detached. A socket that attaches something returns {dispose()}. Each time the VM changes, the fork calls dispose() on the previous return value before calling again, and never looks inside it.
  4. One service per VM. A service read from two places, like the control bar, is kept single with a WeakMap keyed by the VM.
  5. No CSS sockets. Upstream's CSS module class names are hashed at build time and can't be targeted from outside. New parts keep their own classes and styles in the package and use the GUI's public theme variables for color.
  6. No custom files in the fork. Only socket call lines stay in the fork. Tests aren't added to the fork either; they go in this repository's test/ and in the packages.

5. Attaching to the workspace

attachToWorkspace is the socket that attaches features to Blockly and the VM in one go. It is the closest thing to an addon userscript.

8. Relationship with bundled addons

  • Default enablement: site/addon-manifests.ts replaces the fork's generated/addon-manifests through a webpack alias. It enables addons tagged "recommended" plus hide-delete-button and block-palette-icons by default, and keeps hide-flyout off. Choices the user makes in the settings page take precedence.
  • Startup wait: For addons listed in awaitStartupAddons, the runner waits for them to start before moving on.
  • Context menus: createBlockContextMenu in api.js passes items through finalizeHostTransferMenu before finalizing them. This is where the script transfer menu is added.

04 · BUILDING A FEATURE

How to build a new added feature

The steps from deciding where a feature belongs to implementing it in a package, wiring it in the Editor, verifying and shipping it.

1. Decide where it goes

First, decide which path the feature takes to reach the editor. Walk the chart below from the top; the first "yes" is where it goes.

2. Order of work

Publish the implementation from the packages repository first; the Editor upgrades to that npm release and then wires it in. When a new socket is needed, work on the fork change in parallel and pin its SHA in the Editor.

3. Steps

  1. Decide the placement and the socket

    Use Fig. 13 to decide which of A to D applies, and pick the socket from the socket list in the spec. Also decide now which package the implementation goes into. Existing code in the Editor's packages/ is mid-migration; don't use it as a home for new features.

  2. Implement it in a package

    Implement it in the relevant package of turbowarp-plus-packages (or a new package if none fits). Don't import GPL code; receive everything from the editor as arguments. Features that attach something return {dispose}.

    // Package side: receive the document and translations, return a way to detach
export const attachSpriteBadges = (hostDocument, {vm, getMessages}) => {
    const onTargetsUpdate = () => render(hostDocument, vm, getMessages());
    vm.on('targetsUpdate', onTargetsUpdate);
    return {
        dispose () {
            vm.removeListener('targetsUpdate', onTargetsUpdate);
            clear(hostDocument);
        }
    };
};

    Keep styles inside the package under your own classes, and use the GUI's public theme variables for color. Put unit tests in the package too.

  3. Raise the version and publish to npm

    In turbowarp-plus-packages, decide the version with npm run bump (from upstream) or npm run bump:downstream (to propagate downstream), and publish to npm with a v<version> tag. Don't bundle tgz files into the Editor.

  4. (D only) Open a socket in the fork

    Add a line that calls the socket inside a file upstream also has. Write it so that with no value, it behaves like upstream.

    // scratch-gui fork: lines of this shape are the only additions to existing files
const SpriteBadges = getHostIntegration()?.SpriteBadges || null;
// ...
{SpriteBadges ? <SpriteBadges vm={vm} /> : null}

    Don't add new files or tests to the fork. Cover the socket's semantics with tests on the Editor side. If the value should be read as an entry of the integration object, add a host… helper that returns a default to site/gui-integration/lib/tw-plus-integration-points.ts.

  5. Raise the version and SHA in the Editor

    Upgrade package.json and package-lock.json to the npm release. For D, replace the fork SHA in site/source.json with the full 40-character SHA of the commit that opened the socket.

  6. Wire it in site/

    For C, add one line to attachToWorkspace in site/plus-integration.ts.

    attached.push(attachSpriteBadges(hostDocument, {vm, getMessages}));

    For B and D, when passing a UI part, export it from site/gui-integration/index.ts. To toggle it with a startup flag, add one twPlus… flag each to config/feature-flags.ts and config/web-startup-feature-flags.ts, and pass nothing when the flag is off.

    // site/gui-integration/index.ts
export const SpriteBadges = startup.spriteBadges ? SpriteBadgesView : undefined;
  7. For A: register controls from the extension

    A runtime extension can use the control bar without knowing the Editor's internals. In builds without Scratch.gui.stageControls, it should do nothing.

    const controls = Scratch.gui?.stageControls;
if (controls) {
    const button = controls.addButton({
        id: 'my-camera.calibrate', label: 'Calibrate camera', icon: '◎',
        onClick: () => startCalibration()
    });
    button.update({visible: true}); // hidden right after adding
}

    Extensions distributed as packages can use the control bar of @kubohiroya/turbowarp-app-shell, so the same controls also appear in the single-HTML player, which has no toolbar.

  8. Verify

    Pass npm test, npm run typecheck and npm run test:gui-integration, then rebuild with E2E_GUI_ROOT=… npm run build:pages before checking the screen. Don't use stale output left in scratch-gui/build. Check that revision and siteRevision in build-info.json match the current state.

  9. Open a PR

    PRs in this repository have no required checks. With --auto, a PR merges at once without waiting for CI, so look at the CI results before merging.

4. Before you ship

  • The implementation lives in a package, and Editor changes are limited to version bumps and a few wiring lines
  • Everything attached comes off with dispose(), and nothing is attached twice when the VM changes
  • With no value passed in, the fork behaves like upstream TurboWarp
  • GUI internals arrive as arguments; no fork modules are imported
  • Displayed strings have ja and en translations (plus ja-hira where hiragana display is needed)
  • Startup flags are read only from the URL, never from project data
  • Unit tests are in the package; socket tests are in the Editor's test/
  • You checked the screen with freshly rebuilt output

Don't

  • Add new files, custom tests, or CSS that targets upstream class names to the fork
  • Find and rewrite upstream's DOM by class name (that is the addon approach; use a socket if one exists)
  • Import GPL code (the fork, or the Editor's site/) from a package
  • Bundle packages into the Editor as tgz files
  • Run real-mouse E2E tests without being asked

Group action buttons at the bottom right. Place Cancel to the left of the primary action, such as Save or Apply.
