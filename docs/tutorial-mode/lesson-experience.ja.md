# 子どもが迷わない課題の提示方法

課題ごとに、目的、触る場所、使える道具を絞る。Code.org等の教材から参考にするのは、操作箇所の案内だけでなく、課題に必要なブロックだけを提示し、実行して結果を確かめる学習の流れである。

## 一度に示すもの

| 要素 | 提示方法 |
| --- | --- |
| 今の目的 | 「ロボットを スイッチまで とどけよう」のような短い一文 |
| 作品の状態 | 目標と現在位置が分かるステージ。判定に必要な手掛かりは隠さない |
| 編集箇所 | 最初は入力欄一つ。次に短い処理、複数の処理へ広げる |
| 追加できるブロック | 課題ごとの`addableOpcodes`。不要なカテゴリやブロックは並べない。既存コードの実行許可は`executableOpcodes`で別に指定する |
| 次の行動 | 編集中は「ためす」、結果表示後は「もう一度」または「つぎへ」 |
| 支援 | 「ヒント」「見本」「先生をよぶ」を必要に応じて開く |

保存、停止、終了は見つけられる位置に残す。ひとつの行動を説明する場面で、複数の点滅や長いツアーを同時に出さない。Joyrideは場所を示す補助とし、学習全体の進行や達成判定を持たせない。

## 制約の強さを変える

| 段階 | 許可すること | 例 |
| --- | --- | --- |
| 見つける | 読む、対象を選ぶ | 検索で関係する処理を探す |
| 値を変える | 入力欄一つを編集 | 距離、回数、待ち時間 |
| 組み合わせる | 少数のブロックで構造を編集 | 移動と反復を組み合わせる |
| 比べる | 複数の処理やデータを表示 | 二つの探索方法の結果を比べる |
| 設計する | 小さな機能全体を編集 | 新しい場面や注文処理を作る |

迷わせないことと、答えを自動入力することは分ける。意味のある範囲では失敗できるようにし、違う値や別の組み方を試せる。正しいブロック配置を一つだけ照合するより、作品内の目標状態で判定する。

## 結果から次の試行へつなぐ

説明 → 予想 → 編集 → 試行 → 観察 → 再挑戦または達成、を短い循環にする。案内のボタンを押したこと、編集ができたこと、作品が目標を達成したことを別に記録する。

失敗時は「ちがいます」だけで終わらず、「スイッチの少し手前で止まった」等の観測できる変化を示す。ヒントは、場所、考え方、見本の順に深くする。最初から正解の数値や完成プログラムを出さない。見本やスキップを使っても次へ進めるが、自力の試行達成と区別する。

検索を学ぶ課題では、正解の処理一つだけを見せると検索の意味が失われる。学ぶために必要な少数の候補は見せる。二分探索では整列された一覧、DDDでは責務や用語の違いなど、考えるための情報を残す。

## 公開実装から確認できたこと

Code.orgの[Levelbuilderの説明](https://github.com/code-dot-org/code-dot-org/wiki/%5BLevelbuilder%5D-Welcome-to-Levelbuilder)は、初期ブロック、ツールボックス、解答等を別々に編集する入口を持つ。今回も、初期プログラム、追加可能なブロック、保護された判定、課題の説明を別データとして扱う。

確認したCode.orgの`apps/package.json`と公開コード検索ではJoyrideの使用を確認できなかった。非公開部分や過去の全版までの不存在は断定しない。今回のGuideでreact-joyrideを採用する判断と、Code.orgが使うライブラリの事実は分ける。[確認した依存定義](https://github.com/code-dot-org/code-dot-org/blob/staging/apps/package.json)

## 制作者の確認項目

- 最初の一文で、何を変えるかと何を実現するかが分かる。
- 不要なブロック、制御スクリプト、編集パネル、別窓の入口を出さない。
- 必要な手掛かりは残し、試す余地と複数の正解を許す。
- スライダー、ドラッグ、直接の値変更等で目標を迂回できない。
- 実行結果がフィードバックと一致し、次の行動を一つ選べる。
- DSLやDDDの用語は、具体的な操作を体験した後で名前を付ける。
