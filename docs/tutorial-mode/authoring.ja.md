# 実行を続けながら編集する紙芝居教材の作り方

この手順は、Guide統合と編集制限が実装された後に使う制作仕様である。既存の紙芝居DSLとScratch拡張点を使う箇所、これから実装する接続を分けて記す。付属JSONは設定契約の案であり、現行Editorが読める設定ではない。

## 制作物と正本

コースの正本は、作品フォルダ、紙芝居台本、Guideの拡張設定、課題ごとの判定仕様とする。配布SB3と起動URLは、その正本から生成する。作品のJavaScriptへ教材ごとのCSSセレクターや画面座標を埋め込まない。

```text
course-authoring/
  course.json                    コース・章・対応版の制作メタデータ案
  stories/ch01.kamishibai.yaml    紙芝居台本
  project/                       sb3-toolchainの作品フォルダ
    sb3-source.json
    project.source.json
    embedded-extensions.json
    assets/
    extensions/                  現行契約に従う拡張JS等だけを置く
  authoring/guide.settings.json   任意の編集用設定。ビルド時に正本へ同期
  acceptance/ch01.md              判定条件と手動試遊項目
  credits/                       作者・素材・ライセンス
  dist/                          生成したSB3・起動リンク・生成元記録
```

### 拡張設定の保存先

初版の推奨は、作品フォルダの`project.source.json`内にある拡張用保存領域を使い、`extensionStorage.kubohiroyaeditorguide`に設定を保持する方式である。これはGuideの読込・保存契約として追加実装する。SB3では同じデータを`project.json`へ保持し、作品フォルダと往復させる。

固定VM `88a2c06e9deb3dd652c52c20daf4f728b387d41d` の[SB3シリアライズ処理](https://github.com/kubohiroya/scratch-vm/blob/88a2c06e9deb3dd652c52c20daf4f728b387d41d/src/serialization/sb3.js)を2026年11月27日に静的確認した。`serializeExtensionStorage`は、作品で使われる拡張IDの集合に含まれるデータだけを保存する。したがってGuideの設定だけを書いても、拡張が使用中として認識されなければ保存時に落ちる可能性がある。採用時は固定VMでの認識と往復を検証し、設定を持つ作品ではGuideの使用・保存を保証する。内包されるIDや拡張バンドルのnamespace変換も検証する。今回、Guide設定の保存往復は実行していない。

設定を独立ファイルで編集したい場合、`authoring/guide.settings.json`は制作補助とし、生成前に明示的に同期する。独立ファイルと埋め込みデータが異なるときに、暗黙にどちらかを優先しない。

将来、作品フォルダに拡張ごとの設定ファイルを正式導入する場合は、sb3-toolchainとproject-folderの両方で宣言・検証・SB3格納を実装する。現行の`extensions/`は認識対象が制限されているため、任意の設定JSONを追加するだけでは対応したことにならない。

## 1 課題を一文で決める

最初の教材は「ロボットの移動量を変えて、入口のスイッチに届ける」とする。編集可能な入力欄を一つにし、指定値の丸暗記ではなく、予想・試行・結果を体験させる。

| 設計項目 | 第1章の例 |
| --- | --- |
| 最初の状態 | ロボットがスイッチの手前で止まる |
| 変更できるもの | `move-to-switch`スクリプト内の移動量入力 |
| 変更できないもの | 物語進行、試行開始、結果通知、スプライトの削除・名前変更 |
| 達成条件 | 編集後に試し、ロボットがスイッチの範囲へ到着する |
| 複数の正解 | 到着範囲に入る移動量を許可する |
| ヒント | 現在位置とスイッチ位置を見せ、「あと少し」を伝える |
| 復旧 | 試行前の位置へ戻す。学習者の入力値は残す |

## 2 物語役と学習対象を分ける

| 対象 | 担当 | 編集画面での扱い |
| --- | --- | --- |
| StoryController | 紙芝居、Guide呼出し、課題の状態、次章ボタン | 非表示・編集禁止 |
| TrialController | 試行ID、試行開始・終了、判定、初期位置への復帰 | 非表示・編集禁止 |
| Robot | 学習者が変更する短い動作 | 指定スクリプトだけ表示 |
| Switch | 到着を判定する仕掛け | 基本は編集禁止 |
| Guideの固定ハンドラー | 台本とGuideの間の通知 | 非表示・編集禁止 |

初版では、学習者が変える処理を長い「ずっと」ループの実行途中に置かない。編集待ち中は対象の処理が終了済みであることを確認する。試行時に新しい処理として起動し、終了を受け取る。

物語役の「すべてを止める」や緑の旗を課題の進行に使わない。本人が停止ボタンを押した場合は尊重して案内と待ちを片付け、再開方法を示す。

## 3 対象に保存可能な識別子を付ける

`robot`、`move-to-switch`、`move-distance`等の教材内IDを、実際のスプライト・ブロック・入力に対応付ける。表示名だけでは改名や複製に弱いため、対象IDやブロックIDに加えて、期待するopcode・入力名・所属関係を記録する。

Scratchの保存形式で安定したtarget IDが保証されると仮定しない。作者が割り当てた識別子を保持するメタデータと、ビルド時の対応表を使う。ブロックを組み直してIDが変わったら再解決し、曖昧な対応を自動採用しない。設定例の`fixture-*`はダミーであり、配布前に実在する参照へ置換する。

参照切れ、同じ識別子の重複、想定opcodeとの不一致は、教材開始前のエラーとする。対象が見つからないまま、すべてを編集可能にして進めない。

## 4 編集範囲と判定を設定する

[第1章の設定例](examples/lesson-01.proposal.json)を基に、次を記述する。

1. 対応するcourse ID、教材版、必要な機能。
2. 教材内IDと実際のデータの対応。
3. 既定の非表示・編集禁止。
4. 課題ごとの表示対象、変更可能な入力欄、入力制約、新規追加できるopcodeと実行できるopcode。
5. 「ためす」で起動する固定ハンドラーと達成判定。
6. ヒント、見本、スキップ先、次章の識別子。

コースの制作メタデータには、学習目標の概念ID、前提単元、別問題で再び使う場面、次の学習内容を追加する。これらの学習進行情報と、起動時のEditor機能マスクを一つのフラグにまとめない。長期の制作単位は[学習経路](curriculum.ja.md)を参照する。

`addableOpcodes`はパレット・貼付け等で追加できるブロック、`executableOpcodes`は学習対象のコードを試行する前の検査に使う。前者は後者の部分集合とし、ハットとshadowも実行検査へ含める。課題が参照する学習用スクリプトとその呼出し先を検査対象とし、保護されたJudge・物語進行役のコードへ学習用の許可リストを適用しない。第1章は`addableOpcodes: []`で追加禁止だが、既存のハット、移動命令、数値shadowを実行できる。どちらのリストも、`editableFields`や`editableScripts`が与えていない編集権限を広げない。この形式も検査処理も提案段階である。

初版のGuide設定は、任意のJavaScriptやDOMセレクターを実行する形式にしない。クリア条件そのものは保護されたJudgeのScratchスクリプトに置く。設定は通知できる判定役と課題の対応を持つ。新しい条件式エンジンを初版で作らず、[二つのScratchブロックで試行と結果を通知する](completion.ja.md)。

編集してよい入力欄でも、試行終了の報告ブロックや呼出し元は保護する。構造編集を教える章では、切離しや削除で試行が終わらなくなった場合の「試行をやり直す」を用意し、その試行の処理だけを止める。

## 5 紙芝居の場面を作る

既存のDSL 4.0は、`kamishibai`、`assets`、`actors`、`scenes`等で構成する。次は既存教材の形式に合わせた会話部分の最小例で、Guideとの連携命令は含めていない。画像ファイルは別途用意する。

```yaml
kamishibai: '4.0'
assets:
  Gate:
    kind: backdrop
    file: gate.svg
  CatReady:
    kind: costume
    target: Cat
    file: cat-ready.svg
actors:
  Cat: CatReady
scenes:
  opening:
    - stage: Gate
    - Cat.show:
        skin: CatReady
        x: -120
        y: -50
        scale: 60
    - Cat.say:
        text: ロボットが スイッチに とどかないみたい！
        seconds: 3
```

この後の課題進行は、既存Custom Action等の拡張点から固定Scratchハンドラーへ渡す。新しい独自DSL命令を教材ごとに増やさない。

### 接続の概念例

次は実行可能なScratchソースではなく、接続すべき処理を示す擬似コードである。`activity.begin`や`awaitLessonResult`は追加APIの案。

```text
紙芝居: 課題を開始する短いCustom Actionを呼ぶ
  固定ハンドラー:
    activity.begin("gate-distance")
    課題IDと実行世代を記録する
    completeCurrentAction()

紙芝居: awaitLessonResult(課題ID) で物語進行だけを待つ
  Guide: 編集範囲を適用し、対象入力欄を案内する
  学習者: 値を変え、「ためす」を押す
  TrialController: 試行IDを発行し、編集を一時禁止にする
  Robot: 学習対象の処理を新しく実行する
  TrialController: 到着を判定し、同じ試行IDの結果を通知する
  Guide: 未達成なら編集へ戻し、達成なら課題を完了する

紙芝居: 対応する課題の結果を受け取り、次の場面へ進む
```

### 人の操作待ちとCustom Actionの時間制限

確認したAction Registryは`dsl4CustomActionsEnabled`が既定OFFである。対応する公開成果物で明示的に有効化し、能力確認を行う必要がある。既定のCustom Action timeoutは30秒、設定範囲は100〜300000msで、台本から個別変更する契約ではない。

そのため、人が考える時間を長いCustom Actionの中で無期限に待つ実装は採用しない。推奨は、開始操作だけを短いCustom Actionで終え、別のキャンセル可能な「教材結果待ち」へ物語の進行を預ける接続を追加すること。紙芝居側にこの待機を接続する実装と検証が必要である。既存拡張点で成立するかを先に確認し、不足時も新DSLを先に作らない。

最大5分へ延長するだけの試作は、本制作の解決策とは区別する。Guide側だけtimeoutなしにしても、紙芝居側が30秒で失敗する問題は解消しない。

## 6 操作の完了と課題の達成を分ける

| 待つもの | 用途 | 完了にしないもの |
| --- | --- | --- |
| DOMのクリック | ボタンの場所を覚える | Joyrideの「次へ」 |
| 意味のあるGUIイベント | 検索結果を開く、分割表示を作る | 検索欄へのフォーカスだけ |
| 編集の確定 | 指定入力が変更された | 入力欄を触っただけ |
| 対応する試行結果 | 改造が作品の動作へ反映された | 古い試行の遅れて届いた通知 |

課題ID・試行ID・作品の実行世代を照合する。一度完了した通知で次の課題が誤って完了しないようにする。案内を閉じた場合はキャンセルであり、達成にはしない。

## 7 保存と次章への移動を作る

本制作では学習者用の作品フォルダを作り、章末で作品と進行を保存する。進行はcourse ID、教材版、完了またはスキップした課題、次の章を持つ。実行中のPromiseや任意の命令位置は保存しない。

次章のプリセット、course ID、作品の参照を組み合わせたURLを生成する。現行`createEditorURL`は`project_url`等を組み立てられるが、新しいプリセット指定、教材再開、Editorでの自動再生は別の実装事項である。`autoplay`を付ければEditorでも動くと仮定しない。

URLにはブラウザー内のフォルダハンドルを直接格納しない。同一オリジンの作品IDを再解決し、権限が必要なら本人に再接続を求める。保存に失敗したときは次章へ自動遷移しない。ダウンロード保存またはここに残る選択肢を出す。

別の章の配布SB3を開く方式では、前章の変更は自動継承されない。初期試作の独立作品、同一作品の継続、作品を移行する方式を混ぜない。章間の作品移行を行う場合、教材版とデータ変換を検証する。

## 8 対応版を固定して成果物を作る

1. 対応するEditor、Guide、紙芝居、toolchainの公開版と元コミットを記録する。ローカルmainを最新公開版と呼ばない。
2. 素材を用意し、作者・ライセンス・改変内容を記録する。
3. 台本を既存の紙芝居CLIで検証する。CLIとSchemaは同じ対応版を使う。
4. 台本とScratch側の固定ハンドラーを対応する生成経路でSB3へ組み込む。
5. Guide設定を埋め込み、参照解決と必要な機能セットを検証する。
6. SB3からフォルダへ展開し、再びSB3へ戻しても、設定と対象参照が失われないことを確認する。
7. 対象Editorでヘッドレス検証し、生成元、バージョン、ハッシュを成果物と一緒に記録する。
8. 試遊後に配布リンクと教材案内を揃える。公開は別の操作として実施する。

現行Samplesには`update:tutorial-dsl4`等の教材専用生成処理と公開版追従の仕組みがある。新教材はその方針を再利用し、既存教材を上書きしない。新教材用の生成スクリプト名は未確定であり、既存コマンドだけでGuide教材が生成できるとは扱わない。

## 制作完了チェック

- 案内なしでも見せるべき対象が分かり、案内を出すと実際の対象を指している。
- 非表示の制御コードが動き続け、保護したデータは変更できない。
- 入力を確定し「ためす」と、物語を開始し直さず変更が反映される。
- 読む・考える・離席する時間により勝手に失敗しない。
- 失敗、見本、スキップ、停止、作品切替、再開で待ちや表示が残らない。
- 保存、再読込、次章移動後に作品と進行の対応が保たれる。
- 基本の保存、取り消し、終了方法があり、破壊的な抜け道を残さない。
- 小さい画面、キーボード、日本語入力、音なしの条件でも課題を進められる。
