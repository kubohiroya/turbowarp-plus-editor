# 作品内の判定処理とクリア通知の最小構成

クリア条件は教材作者が通常のScratchブロックで書き、子どもの表示・編集範囲から外した判定用スプライトに置く。Editorは条件式を解釈せず、試行の識別、通知元の確認、結果の受理、待機の解除を担当する。初版で新しい条件DSLや常時DOM監視を作らない。

## 作品とEditorの分担

| 作品内の保護された処理 | GuideとEditor |
| --- | --- |
| 初期位置・得点・課題の状態を初期化する | 現在の課題を有効にする |
| 子どもが編集した処理を新しく呼び出す | 試行ごとに一意のトークンを発行する |
| 座標、接触、順序、個数等から達成を判定する | 指定した判定用スプライトからの通知だけ受ける |
| クリアまたは再挑戦を通知する | 古い試行・二重通知・停止後の通知を拒否する |
| 作品内の成功演出を行う | 紙芝居へ結果を返し、学習記録を残す |

Code.orgのMazeには、アプリ側の`resultsHandler`から成功を判定し、試行結果を報告する実装がある。すべての教材で「隠された子ども向けブロック」が判定を担当するとは限らない。今回、作品内に判定スクリプトを置くのは、Scratchの既存機能で教材を作れるようにする選択である。[公開ソース](https://github.com/code-dot-org/code-dot-org/blob/staging/apps/src/maze/maze.js)

## 追加するScratchブロックは二つ

| ブロック案 | 種類 | 用途 |
| --- | --- | --- |
| 課題［ID］の試行を始める | レポーター | 今回の試行トークンを取得する |
| 試行［トークン］の結果を［クリア／再挑戦］と知らせる | 命令 | 保護された判定処理から結果を通知する |

単に「課題IDをクリアする」一つだけでは、前の試行の遅れた通知と今回の通知を区別できない。試行開始のレポーターを一つ足し、結果通知と合わせた二つを推奨する。トークンは判定役のローカル変数へ保持する。

子ども向けパレットには、この二つのブロックを出さない。さらに、ブロック呼出しの`util.target`で、実際の実行元が設定済みの判定役であることを確認する。利用者が渡すスプライト名や文字列を通知元の証明にしない。初版では判定役のクローンからの通知も受けない。

## 第1章の組み方

学習用のRobotには、編集対象の短い移動処理だけを置く。Judgeには試行管理と到着判定を置く。初版は保護する処理を別スプライトへ集め、同じスプライト内のスクリプトを細かく隠す作業を減らす。

```text
「ためす」が押されたとき
  すでに試行中なら何もしない
  Robotの位置と仕掛けの状態を初期化する
  トークン ← 課題［gate-distance］の試行を始める
  Robotへ「今回の移動を実行」を送る
  到着、処理終了、または計算上限まで作品の状態を調べる
  もし Robotがスイッチの範囲に入っている なら
    ゲートを開く
    試行［トークン］の結果を［クリア］と知らせる
  でなければ
    試行［トークン］の結果を［再挑戦］と知らせる
```

これは接続の擬似コードであり、配布済みのScratch作品ではない。到着判定は、例えば標準の「Robotのx座標・y座標を調べる」と比較・論理ブロックで書ける。判定役を画面外に置いたりScratchの「隠す」を使ったりすることと、編集画面から隠すことを分ける。接触判定を使う場合も、判定用スプライトの可視状態による影響を確認する。

待つのは物語の進行だけとする。人が編集する時間には試行の計算timeoutを適用しない。計算の上限に達した場合も、その試行だけを中断し、課題の編集へ戻す。VM全体の停止や緑の旗を通常の試行に使わない。

## クリアを迂回するUI操作を止める

| 入口 | 初版の制限 | 止める位置 |
| --- | --- | --- |
| ステージ上のドラッグ | 禁止。クリック等の教材入力は残す | ドラッグ開始前。位置・表示・重なり順を変える前 |
| プロパティパネル | 座標、向き、大きさ、表示等は読み取り専用 | 入力部品と、その書込みコールバック |
| 変数・リストパネル | 値、定義、要素の直接変更を禁止 | 値・追加・削除・取込みの書込みport |
| 変数モニター | 数値は表示可能。スライダーと値の変更を禁止 | モード切替と値更新の両方 |
| リストモニター | 読み取り専用 | 要素編集、追加、削除、ファイル取込み |
| パレット | `addableOpcodes`にあるブロックだけを表示 | カテゴリ単位に加えて個々のブロックを絞る |
| 貼付け・バックパック等 | `addableOpcodes`以外の追加と許可外の構造変更を拒否 | VMへブロック変更を反映する前 |
| 既存の禁止ブロック | `executableOpcodes`にないコードを黙って実行しない | 学習対象とその呼出し先を検査し、試行開始を拒否 |
| ワークスペース上の直接実行 | 原則禁止 | ブロックをクリックして処理を起動する入口 |

固定GUIの`stage.jsx`は、編集用ドラッグでは`target.draggable`がfalseでも開始できる条件を持つ。したがって「ドラッグできない」設定だけでは足りない。`onStartDrag`で、`goToFront`、`startDrag`、ドラッグ中の非表示化より前に課題の許可を確認する。

ネイティブの変数・リストモニターには、値を更新する呼出しがある。Plusのプロパティ・変数パネルにも別の書込み経路がある。VMの一つのメソッドを包むだけで全経路を防げるとは扱わず、各所有パッケージのUIと操作portに同じ許可を渡す。

固定GUI `60b87e2f2503206847f509285aa4de3cee3670c7`では、`slider-monitor.jsx`、リスト編集、モニターのCSV取込みが`variable-utils.js`の`setVariableValue`を呼び、同関数は`variable.value`を直接更新する。2026年11月27日に静的確認した時点で、ここにGuideの許可確認はない。共通の書込み前に汎用portを置き、Guideから受け取る判定を結線する案を検討する。さらにスライダー等の操作UIを無効化し、別経路を持つPlusの各パネルにも同じ判定を渡す。[スライダーの入口](https://github.com/kubohiroya/scratch-gui/blob/60b87e2f2503206847f509285aa4de3cee3670c7/src/containers/slider-monitor.jsx)・[共通の書込み関数](https://github.com/kubohiroya/scratch-gui/blob/60b87e2f2503206847f509285aa4de3cee3670c7/src/lib/variable-utils.js)

一方、学習者の許可されたプログラムやJudgeによる変数更新・移動は実行できる必要がある。VMの変数や座標そのものを凍結したり、`set x`等のプリミティブを全体から削除したりしない。人による直接変更と、許可されたプログラムの実行を区別する。

### 一つの編集ポリシーを各入口へ渡す

Guideが、課題ごとの`canMutate`判定を提供し、ホストが各入口へ渡す構成を推奨する。例えば`stage.drag.start`、`sprite.property.write`、`variable.ui.write`、`monitor.mode.change`、`block.field.write`を区別する。操作元の情報は各ホストの結線で付け、作品が渡す文字列を信用して許可を広げない。学習モードで未定義の変更操作は拒否し、通常モードでは従来の動作を保つ。

初版はステージ・プロパティ・変数の直接変更を一律禁止にし、ブロック入力欄の許可リストだけを実装する。個々の変数の書込み許可は、その学習課題が必要になる段階で追加する。

`addableOpcodes`が空なら新規追加を禁止するが、既存コードの実行までは禁止しない。第1章の`executableOpcodes`には既存ハット、移動命令、数値shadowを含め、指定した入力欄だけを編集できるようにする。追加可能なopcodeは実行可能なopcodeにも含める。実行検査は学習用コードに適用し、保護されたJudgeや物語進行役は別に管理する。

`data_setvariableto`や`data_changevariableby`をパレットから隠すだけでは、既存ブロックや貼付けを防げない。実行可能なopcodeに加え、書込み先の変数IDも検証する。カスタムブロック経由の更新がある課題では、呼出し先も対象にする。Judge専用のローカル変数は、学習用コードの許可対象に含めない。

隠したbroadcast名を知っていることは権限の証明にしない。Judgeがbroadcastを受けても、今回の実際の状態を確かめてからクリアを知らせる。

## ハイスコアのスライダーによる迂回

「ハイスコアを表示 → スライダー表示へ変更 → 値を上げる」は必須の受け入れケースとする。保存済み作品が最初からスライダー表示である場合も含め、読み取り専用へ正規化し、実際の値更新も拒否する。

表示してよい変数IDも許可リストにする。表示用の得点は読めても、Judgeの内部フラグや集計用リストはモニターの候補に出さない。読み取り専用であることと、何を見せるかも分ける。

表示用のハイスコアだけをクリア条件にしない。Judgeは今回の試行で得た得点を自分のローカル変数・リストで管理し、正規の作品内イベントから更新する。例えばコインの取得なら、接触状態と未取得のコインIDを確認して一度だけ加点する。「得点した」という学習用コードからのbroadcastだけを無条件に信用しない。

ハイスコア表示は判定結果の写しとして更新する。今回の得点、過去のハイスコア、課題達成は別に扱う。変数の扱い自体を学ぶ課題では、許可する変数・操作・範囲を明示して解放する。

## 結果通知の最小API

Guide内に、DOMやJoyrideから独立した小さな試行ストアを置く。

```text
activate(activityId)                       ホストが課題を開始する
beginTrial(activityId, actualCaller)        判定役へトークンを返す
report(token, cleared | retry, actualCaller) 結果を一度だけ受け付ける
waitForClear(activityId, signal)            紙芝居の進行役が待つ
subscribe(listener)                        記録やフィードバックへ通知する
cancel(reason)                             停止・作品切替等で解除する
```

結果が待機登録より先に届いても、現在の課題の完了を保持して取りこぼさない。課題を開き直す、作品を停止する、作品が切り替わると古いトークンを無効化する。再挑戦は物語全体の失敗にしない。通知を受理することと、紙芝居の長時間待機へ接続することは別の実装である。

既存のGuideの`notify(targetId, event)`はGUI対象に結び付くため、クリア通知へ流用しない。対象GUIが消えても、試行結果や学習記録が失われないようにする。

## 最小改修と確認状況

| 範囲 | 状況・次の作業 |
| --- | --- |
| Guide試行ストアと二つのScratchブロック | 旧草案には通知元、古い通知、二重通知、先着通知、再挑戦、取消、VM停止の単体確認記録がある。現ソースとの対応は未確認 |
| Guideの既存検証を含むテスト | 旧草案は16件・型確認・バンドル生成の成功を記すが、対象SHA・実行日・ログは未特定。本版の検証済み結果には含めない |
| 作品内のJudge | 通常のScratchで制作可能。第1章の実作品はこれから作る |
| 判定役の非表示・編集禁止 | 対象一覧、検索、タブ等の範囲制御が必要。未実装 |
| パレット・各書込み入口の制限 | 各機能パッケージと必要最小のGUI接続を追加する。未実装 |
| 実作品での再生継続、スライダー迂回防止 | 製品Editorのヘッドレス結合確認が必要。単体検証だけでは完了としない |

旧草案は承認済みGuideパッケージのローカル試作として記していたが、今回そのソース履歴と検証ログを確認できなかった。再確認時はGuideのコミットSHA、未コミット差分の有無、実行日、コマンド、ログを対応付ける。今回の文書保存では、製品への組込み、実作品の実行、Guideの単体検証を行っていない。作品を別のEditorで改変することや同じページの任意のJavaScriptまで防ぐものではなく、学習用Editorの通常操作による迂回を防ぐ範囲とする。

今回静的確認した箇所は、上記固定GUIの[ステージのドラッグ](https://github.com/kubohiroya/scratch-gui/blob/60b87e2f2503206847f509285aa4de3cee3670c7/src/containers/stage.jsx)、ネイティブの[モニターとCSV取込み](https://github.com/kubohiroya/scratch-gui/blob/60b87e2f2503206847f509285aa4de3cee3670c7/src/containers/monitor.jsx)、[リスト編集](https://github.com/kubohiroya/scratch-gui/blob/60b87e2f2503206847f509285aa4de3cee3670c7/src/containers/list-monitor.jsx)と共通の書込み関数である。sprite-panesのプロパティ・変数・クローン等の経路は別途監査し、同じ許可を渡す。判定規則はGuide、UI部品と更新処理は各所有パッケージ、GUI側は必要最小の接続を担う。
