# 紙芝居からDSLとドメイン設計へ進む教材

TurboWarp-kamishibai-docsの既存チュートリアルと詳細ガイドへ接続する橋渡し教材を追加する。新しいマニュアルを複製せず、短い作品の改変から「紙芝居に必要な言葉とルールを、どうコンピューターへ伝えるか」を体験する。

追加はE01〜E08の8単元案とし、既存27単元と合わせて35単元の候補とする。単純な一直線にはせず、導入後に紙芝居制作を選べる分岐を置く。後半のDDDは、手続き・データ・仕様を扱った後に進む。

## 8単元の構成

| 単元 | 子どもが行う作業 | 学ぶ内容 | 解放する範囲・道具 |
| --- | --- | --- | --- |
| E01 紙芝居の舞台裏 | せりふ一つを変え、上演結果を比べる | 作品と台本の対応 | 練習用台本のせりふだけ。ブロック版チュートリアルへ |
| E02 みんなの言葉帳 | 場面、登場人物、素材、命令のカードを分け、作者に説明する | ドメイン知識と共通の言葉 | 必要な定義を読み取り表示。小さな用語帳 |
| E03 二つの台本 | 同じ場面をブロックとYAMLで読み比べる | DSL、表現、構文と意味 | 練習用文書と比較表示。文書編集の能力を追加 |
| E04 台本の約束 | 名前の不一致や存在しない移動先を一つ直す | 型、参照、構文検証と意味検証 | 一つの参照と診断だけを編集・表示 |
| E05 同じ登場人物かな | 衣装を変えても同じ人物か、別の人物かを説明する | 識別、EntityとValue Objectの入口 | 人物IDと衣装・位置等のデータを表示 |
| E06 三つの仕事場 | 台本制作、上演、学習進行で「場面」「完了」の意味を比べる | 責務、モデル、Bounded Context | 小さな責務表と接続図。データベースやクラスの実装を先に要求しない |
| E07 台本をこわさず直す | 場面名の変更と参照更新をまとめ、ルールが守られることを試す | 不変条件、変更の整合性、集約の考え方 | 関連する定義・参照と小さなテスト |
| E08 新しい演出の注文 | 「もっと驚く登場」の要求を整理し、既存命令の組合せで表現する | モデルを育てる、DSLの適用範囲、互換性 | 仕様・試行・差分。必要な場合だけ既存Custom Actionの拡張点を検討 |

E01〜E04は導入後の分岐に置ける。E05〜E08は基礎編の手続き・データと、工学編の仕様・テストを必要な前提にする。DDDを全機能の解放条件にはしない。

## 子どもが体験する言葉から始める

| 最初の説明 | 後で結び付ける概念 |
| --- | --- |
| 紙芝居には、どんな役や決まりがある？ | ドメイン知識 |
| 作者とプログラムで、同じ意味の言葉を使おう | ユビキタス言語 |
| 紙芝居を書くための言葉を使おう | DSL |
| 衣装が変わっても、この人は同じ人？ | Entityと識別 |
| 同じ位置や時間なら、同じ値と考えられる？ | Value Object |
| 台本を作る仕事と、上演する仕事を分けよう | 責務とモデルの境界 |
| 名前を変えるなら、つながりも一緒に直そう | 不変条件と整合性の境界 |

DSLは特定の問題領域を表すための言語で、テキストに限らない。YAMLは表記の土台であり、紙芝居の語彙と規則のすべてではない。[DSLの説明](https://martinfowler.com/bliki/DomainSpecificLanguage.html)

DDDでは、その領域を知る人と開発者が言葉とモデルを確かめ、理解に応じて育てる。単にクラス名を紙芝居の単語へ変える作業にしない。[共通の言葉](https://martinfowler.com/bliki/UbiquitousLanguage.html)

人物や場面を常にEntityと決め付けない。この教材のモデルで何の同一性を保つ必要があるかを考える。値が等しいことと、同じ対象であることの違いを扱う。[識別と値の分類](https://martinfowler.com/bliki/EvansClassification.html)・[Value Object](https://martinfowler.com/bliki/ValueObject.html)

## モデルの境界を紙芝居で考える

以下はDDDを学ぶためのモデル案であり、現在の紙芝居AppがこのDDD構造で実装されているという説明ではない。

| 仕事場のモデル案 | 扱うもの | 扱わないもの |
| --- | --- | --- |
| 台本制作 | 場面定義、人物、素材参照、命令、台本の妥当性 | 今回の再生位置、子どもの学習達成 |
| 上演 | 一回の再生、場面遷移、実行中の状態、演出の終了 | クラスの課題割当、台本の編集権限 |
| 学習進行 | 課題、試行、クリアの証拠、解放、教員の評価 | アニメーションの描画、紙芝居の構文処理 |

「場面を再生した」「場面を編集した」「課題をクリアした」は別の出来事である。上演側の終了を、そのまま学習の達成にしない。境界はUIのタブやスプライトの数から機械的に決めず、言葉とルールの意味がそろう範囲で考える。[Bounded Context](https://martinfowler.com/bliki/BoundedContext.html)

集約は何でも一つの大きなオブジェクトにまとめる意味ではなく、どの変更を一緒に整合させる必要があるかを考える発展課題にする。図を作っただけでDDDを実践済みとはしない。作者への説明、ルールの検証、別の要求への変更を到達の証拠にする。

## 教材進行と練習用台本を分離する

学習者が編集する紙芝居を、教材自身の進行台本と同じものにしない。進行役とJudgeは保護し、練習用台本だけを検査・再生できるプレビューまたは別セッションを用意する。既存資料には、台本を変更した後に開始し直して反映する手順がある。これを、教材進行役も開始し直す指示として流用しない。

最初の接続版は、課題の説明と保存したチェックポイントから既存チュートリアルへ進み、終えたら戻る方式でもよい。その場合は中断と再開を明示する。同じ画面で教材を再生し続ける完成形には、実装計画T13のセッション分離が必要である。

既存資料の「フォーム編集で開く」等は、別のEditorへ直接移るリンクを含む。学習モードの制限や保存先が自動継承されるとは扱わない。今回の教材用起動リンクは、対応するホスト、能力、教材設定を指定して生成する。既存Docsのリンクは無断で書き換えない。

## 制作と評価

各課題は、読む箇所、変更する一つの対象、試すこと、戻り先を持つ。詳しい命令表を教材内へ丸ごと複製せず、TurboWarp-kamishibai-docsの該当ガイドへ案内する。子ども向けの短い説明と、制作者・教員向けの正式用語を対応付ける。

DSLの課題は、台本の検査と練習用の上演結果で判定できるものを自動判定する。ドメインの用語や境界の設計は複数の妥当な答えがあるため、説明・例・反例を小さなルーブリックで教員が見る。マニュアルを開いたことや用語を入力したことを習得の証拠にしない。
